05Method

(05) MethodFive rules, found in the code

I don't have a manifesto. I have repositories.

Reading them back, the same rules keep coming up. Here they are, each with the evidence.

I

Honesty

I write down what works. And what doesn't.

A README that only lists features is an advert. Mine have a “what doesn't work” section, and in the research projects every claim carries a label: tested, untested, not implemented.

  • yag — “What works today” and “What doesn't”, side by side
  • middleManPS4 — it used to be called fwSpoofer; the name changed because it spoofs nothing
  • piko — a list of known limitations longer than the feature list
A command recorded as sent doesn't prove it was received.

II

Consent

Nothing happens without asking.

When software acts in someone else's name, it has to ask first. Not once in the settings: every time, at the moment it matters.

  • piko — no run without a per-app permission and an approved plan
  • piko — password and credential windows are refused
  • synk — the waiting list only contacts people who gave consent, for 30 days at most
No autonomous default.

III

Data

Your data stays at your place.

If something can run locally, it runs locally. The cloud is a choice to justify, not a starting point.

  • Brat Animator — no backend: audio and video never leave the tab
  • synk — on-premise, PostgreSQL on the salon's PC; the local AI is off by default and never sees client notes
  • piko — local inference only, screenshots one at a time and only on request
Your machine is the render farm.

IV

Tools

Boring on purpose.

I pick the most boring tool that does the job, and I write down what each project deliberately won't do. Fewer dependencies, fewer surprises.

  • yag — C17, libcurl, pthreads: it never runs a model and never will
  • middleManPS4 — zero runtime dependencies, standard library only
  • This site — no framework, no build step, no runtime dependencies
That's not a limitation. That's the scope.

V

Uncertainty

If I don't know, it shows.

Real systems fail halfway. I'd rather show an uncertain state than pretend everything went fine: someone can deal with what they can see.

  • synk — a slot is never assumed free if Calendar doesn't answer reliably
  • synk — “queued” is not “synced”: pending and attention states are visible in the dashboard
  • yag — the model list is not a health guarantee, and it says so
Queued is not confirmed.

(vi) Process

How a project goes, usually.

  1. i.

    I ask why

    Before how. A clear problem saves weeks of features nobody asked for.

  2. ii.

    I write down the limits

    What it does, what it won't do, what could go wrong. It's the first file in the repository.

  3. iii.

    I build and test

    Small steps, automatic tests, CI on every push. If it isn't verified, it's labelled as such.

  4. iv.

    I hand it over clean

    Installers, checksums, documentation in Italian when the user is Italian. And a list of what's still open.
